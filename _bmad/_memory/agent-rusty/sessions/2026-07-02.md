With the monolith available, went back through Part 1's "unverified" rows and got real permalinks. Concrete new results (all in BOND.md gap table with full permalinks):

- ✅ **Confirmed correct**: `assignee_type IN ('user','team')` — matches `GroupAssignee.user_id`/`.team` exactly. Substatus 7-value enum — matches `types/group.py` `SUBSTATUS_UPDATE_CHOICES` 1:1.
- ⚠️ **Upgraded from "can't verify" to "concrete gap, cited"**: regression suppression for `resolvedInNextRelease`. Real Sentry (`GroupResolution.has_resolution`, `event_manager.py:_handle_regression`) is semver/date-aware; Rustrak does naive release-string equality. A rollback/older-release event would wrongly reopen an issue in Rustrak but not in real Sentry.
- ❌ **New, real gaps found**:
  - Bulk mutation cap: Rustrak hardcodes 100 with a comment claiming it mirrors Sentry's UI cap — real Sentry's `BULK_MUTATION_LIMIT` is 1000. The comment's claim was simply wrong.
  - Priority default for missing/unrecognized `level`: Rustrak defaults `None`→"high", unknown string→"low". Real Sentry's `_get_priority_for_group` falls through to `MEDIUM` in both cases. Small, mechanical, easy fix.
  - `/issues/{id}/hashes` response shape: Rustrak returns raw `Grouping` rows; real Sentry returns `{id: primary_hash, latestEvent, mergedBySeer, seerMatchDistance}` per hash, paginated. Also note: this endpoint is `@deprecated` in real Sentry now.
  - `/issues/{id}/tags/{key}` response shape: Rustrak wraps as `{key, values}`; real Sentry returns a bare list of `{key, name, value, count, lastSeen, firstSeen}` (camelCase).
