## Session — tracing standalone Span envelope item ingestion ([TR], scoping Rustrak span support from scratch)

**What happened:** Full pipeline trace of `ItemType::Span` (standalone OTel-style span, not embedded in a transaction) through relay-server. Rustrak currently has zero span support, so this is ground-truth for a from-scratch implementation. Used 4 parallel/sequential subagents (pipeline trace, schema+rate-limit, fixtures, and a reconciliation pass) against relay-repo SHA f42b1c8a15bba8cb96d1dfd3bd2b3158c7817c5f.

**Key findings:**
- **Two live pipelines handle `ItemType::Span`, gated by `Feature::SpanV2ExperimentalProcessing`** (relay-server/src/processing/relay.rs:127-131). This was the single most important discovery — neither prior BOND.md note nor the initial task framing anticipated it.
  - **`processing/legacy_spans/`** — the DEFAULT (feature flag off). Handles a V1 `Span` struct. DSC is optional (`Option<&DynamicSamplingContext>` throughout, no `MissingDynamicSamplingContext` error variant exists in `legacy_spans::Error` — relay-server/src/processing/legacy_spans/mod.rs:28-38).
  - **`processing/spans/`** — the NEW pipeline (opt-in). Converts to `SpanV2` internally. DSC is REQUIRED — `Error::MissingDynamicSamplingContext` on absence, except when `client_is_relay` (internal OTel integration carve-out) — relay-server/src/processing/spans/dynamic_sampling.rs:68-114.
- This resolved an apparent contradiction: schema/rate-limit subagent found test fixtures accepting spans with NO DSC header; pipeline-trace subagent found DSC required in source. Both correct — different pipelines. The DSC-less tests in tests/integration/test_spans.py never set the V2 feature flag, so they exercise `legacy_spans` (today's real-world default for actual SDK traffic).
- V2 pipeline order (closely matches Sentry's documented validate→DSC→expand→normalize→filter→ratelimit→store shape): prepare_envelope → attachment feature filter → validate (duplicate item) → expand (parse+convert to SpanV2, dedup by span_id) → DSC check → dynamic sampling decision → normalize (eap normalizers) → inbound filters → PII scrub → normalize-derived/trim/schema-validate → rate limit (Span then SpanIndexed) → metrics extraction/split → store (Kafka via StoreSpanV2).
- DataCategory::Span (=12, coarse ingest quota) vs DataCategory::SpanIndexed (=16, full-storage quota) — checked Span first (hard reject whole batch on breach), SpanIndexed second (soft: keep total-count metrics, drop indexed detail) — relay-base-schema/src/data_category.rs:77-108, relay-server/src/processing/spans/mod.rs:599-655.
- Segment/trace assembly is NOT done at this stage in either pipeline — `is_segment` is a pass-through flag used only for metric tagging and per-span normalization branching. True segment-tree/trace assembly is deferred to a downstream stage (Snuba/EAP), not Relay's ingestion processors.
- V1 `Span` struct (relay-event-schema/src/protocol/span.rs:19) has both `segment_id` + `is_segment`; V2 `SpanV2` (relay-event-schema/src/protocol/span_v2/mod.rs:14) dropped `segment_id` as a top-level field — it lives as attribute `sentry.segment.id` instead.
- Exact numeric size/count limits (max_span_size, max_container_size, trimming.span.max_size default) live in `relay-config`, which is NOT in this sparse checkout — could not confirm concrete byte values. This is a checkout gap, not a "doesn't exist" finding.
- `~/.rusty/relay-repo/` is 20 commits behind `origin/master` (f42b1c8a1 → 9b930e710) as of this session — diff scope not yet checked, flagged to Abian at start of session per standing order.

**Rustrak gaps confirmed:** Standalone Span ingestion is entirely unimplemented (already known, BOND.md pre-existing row). This session converts that from a one-line gap into full pipeline ground truth Abian can build against. Recommend Rustrak model against `legacy_spans` semantics first (today's real default: DSC optional, V1-shaped Span fields) since that's what actual Sentry SDKs hit in production today, while being aware SpanV2/the newer pipeline is Relay's forward direction if strict future-compat matters.

**Follow-up:**
- Consider sparse-checking out `relay-config` and `relay-spans` crates next time span limits or OTel-conversion details matter — both were referenced but not present in the current sparse checkout.
- `relay-server/src/processing/legacy_spans/` was only spot-checked for DSC handling, not deep-traced stage-by-stage the way `processing/spans/` was. If Rustrak decides to implement legacy-pipeline semantics exactly, a follow-up `[TR]` on `legacy_spans/` specifically (validate/normalize/filter/ratelimit/store stage order + limits) would be worth doing.

## Session — Full standalone Span field reference for future Rustrak span ingestion (deep [SE] dive)

**What happened:** Abian asked for a from-scratch, field-by-field reference of Relay's Span data model to plan standalone span ingestion in Rustrak (currently zero span support beyond silently accepting `ItemType::Span` — see BOND.md gap table). relay-repo SHA `f42b1c8a15bba8cb96d1dfd3bd2b3158c7817c5f` (a `git fetch --dry-run` shows master has since moved to `9b930e710` — **pending update, not pulled this session**, findings below are pinned to `f42b1c8a1`). Spawned 4 parallel research subagents covering: legacy `Span`/`SpanData` struct (span.rs), `SpanV2`/`Attributes` struct (span_v2/), the conversion layer + which pipeline is authoritative today (relay-spans crate + processing/spans vs processing/legacy_spans), and normalization limits + real test fixtures. Full findings delivered to Abian as the task deliverable (not duplicated here — see his conversation for the complete field tables and permalinks). Distilling only the non-obvious, reusable insights below.

**Key findings:**
- **Two live span schemas coexist, and it's a feature-flag switch, not a version bump.** Legacy `Span` (`relay-event-schema/src/protocol/span.rs`) is authoritative for standalone span ingestion **by default, today** — `LegacySpansProcessor` claims all bare `ItemType::Span` items first (`relay-server/src/processing/relay.rs#L126-131`) unless the project has `Feature::SpanV2ExperimentalProcessing` (`projects:span-v2-experimental-processing`), in which case `SpansProcessor` (SpanV2-native) claims them instead. Both processors match the *identical* item predicate (`ItemType::Span && !is_container`) — order-of-registration is the only tiebreaker. For a from-scratch Rustrak implementation aimed at "what a Sentry SDK sends today," **legacy `Span` is the correct target**, not SpanV2.
- **SpanV2 is real and already has its own container wire format** (`ItemType::Span` + `content_type: application/vnd.sentry.items.span.v2+json`, JSON object `{"items":[...],"version":2,"ingest_settings":{...}}`, NOT NDJSON) — worth knowing exists, but not the near-term implementation target.
- **`SpanData` is NOT a generic bag** — it's ~80 explicitly named, typed OTel/GenAI-convention fields (gen_ai_*, db_*, http_*, user_geo_*, lcp_*, messaging_*, etc.) each with a `field = "dotted.wire.name"` + often `legacy_alias`, PLUS a catch-all `other: Object<Value>` via `#[metastructure(additional_properties, retain = true, skip_serialization = "null")]` (span.rs L942-948) for anything unrecognized. A naive "just store `data` as JSONB" Rustrak implementation would technically accept everything (the catch-all covers it) but would miss the PII-scrubbing semantics tied to the named fields (`pii = "span_data_pii_from_conventions"`, resolved per-key via `relay_conventions::attribute_info`).
- **No `duration` field exists on `Span`** — it's *always* derived as `timestamp - start_timestamp` (confirmed via the `Getter` impl, span.rs ~L142-197). Rustrak must compute this, not expect it on the wire.
- **`description` has no schema-level `max_chars`** (unlike `op`/`origin`, both capped at 128 chars, span.rs L33/L79) — truncation happens downstream in `relay-event-normalization/src/normalize/span/tag_extraction.rs` (`truncate_string`, byte-based, char-boundary-safe, replaces last char with `*`), default `max_tag_value_size = 200` (only confirmed from test scaffolding — the canonical default lives in `relay-config`, not in this sparse checkout).
- **`relay-config` and `relay-spans` are outside the current sparse checkout** (`git sparse-checkout list`: only relay-base-schema, relay-event-normalization, relay-event-schema, relay-monitors, relay-protocol, relay-server/src, tests). The subagent worked around `relay-spans` via `git show <sha>:relay-spans/src/...` (read-only, no working-tree pollution) to trace `span_v1_to_span_v2` / `otel_to_sentry_span`. If Span↔SpanV2 conversion or config defaults (`max_span_size`, `max_tag_value_length`) come up again, either add `relay-config`/`relay-spans` to the sparse-checkout set permanently, or keep using `git show` for one-off reads.
- **Pending relay-repo update not pulled**: `git fetch --dry-run` showed `f42b1c8a1..9b930e710` on master, plus a submodule access failure (`Could not access submodule 'relay-conventions/sentry-conventions'` — the PII-convention lookups referenced above depend on this submodule's data and were *not* independently verified past the field-name-to-convention-key mapping in span.rs itself).

**Rustrak gaps confirmed:** none newly fixed (this was a forward-looking reference dive, not a live audit) — reinforces the existing BOND.md row "`Span` (standalone) — Different schema (`SpanV2`)" which undersold the picture: the *actual* default-path schema to implement against is legacy `Span`, with SpanV2 as a documented future direction, not "the" schema.
