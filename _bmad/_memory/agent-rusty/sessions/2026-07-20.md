# Session 2026-07-20

## Context

Abian asked for a state-of-the-branch review on `feat/project-config` (all work
uncommitted at session start), then to verify the platform-override work was
actually aligned with Sentry.

## What was audited

`project.platform` manual override, added 2026-07-03. BOND had it recorded as
`✅ Implemented`, so per standing orders I did not re-investigate it — I checked
only the one claim never source-verified: what real Sentry validates a *manual*
override against.

## Headline finding

The 2026-07-03 implementation validated the manual override against Relay's
`VALID_PLATFORMS`. That is a **category error**, not a short list:

- Relay's 19 constrain an **event's** `platform` field. Anything outside them is
  deleted and replaced with `"other"` (`event.rs:1188-1199`, SHA `c455da18`).
  `javascript-nextjs` can never appear there.
- A **project's** platform is product config. Sentry validates it via
  `Project.is_valid_platform` → `GETTING_STARTED_DOCS_PLATFORMS` (109), a list
  it maintains by hand in sync with `static/app/data/platforms.tsx`.

Only 9 ids overlap. Rustrak was returning 400 for ~100 platforms Sentry accepts.

Also found an upstream Sentry inconsistency worth *not* copying: auto-detection
filters on the 19 while the picker offers the 109, so a Perl event sets a
project platform the settings picker then refuses to re-select. Rustrak now uses
the union (119) to keep auto-detected values selectable.

## Process notes worth keeping

- **The stale doc comment was the tell.** `VALID_PLATFORMS` carried a comment
  justifying the narrow list with "the manual project-creation picker, which
  Rustrak does not implement" — which Abian's own change had just falsified. A
  comment that argues from an absent feature is a landmine the moment that
  feature lands. Worth grepping for that shape after any feature addition.
- **Mutation-tested the regression test.** The new auto-detection test passes on
  unmodified code, so it proves nothing on its own. Pointing
  `infer_platform_from_event` at the wide list made it fail as intended. Do this
  whenever a test is written for behavior that is already correct.
- **`mv` restoring a `.bak` kept the old mtime**, so cargo did not rebuild and
  the suite reported 2 failures against a stale mutated binary. `touch` fixed
  it. Nearly reported a false failure — always `touch` after restoring a file.
- Abian pushed back hard, and correctly, on "no hace falta clonar las 109". The
  recommendation was reasoning from Sentry's *motivation* for the list (docs
  onboarding, which Rustrak lacks) instead of Rustrak's *use* for it (letting a
  user name their stack). Also called out loose wording: I wrote "your 9
  platforms" for ids that are Relay's, which muddled the whole explanation.
  Lesson: when the owner says the current state may be wrong, argue from source
  only, and never let the existing implementation frame the vocabulary.

## Left open

- `platforms.ts` mirrors the Rust list by hand — same drift risk Sentry has.
  Could be generated at build time from the OpenAPI spec.
- Platform cannot be cleared (`Option<String>` means null = unchanged). Sentry
  allows it. Low value, recorded in BOND.
- Combobox verified by typecheck, lint and `next build` only. Not yet exercised
  in a browser.
