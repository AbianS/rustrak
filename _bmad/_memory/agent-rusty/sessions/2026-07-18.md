## Session — prod incident: `events_issue_id_digest_order_key` collisions

**What happened:** Abian pasted a wall of production `23505` unique-constraint errors (`Failed to digest event ... duplicate key value violates unique constraint "events_issue_id_digest_order_key"`), asked what they mean. This is a pure Rustrak implementation bug, not a Sentry-protocol compat question — investigated directly against `apps/server/src`, no Relay/monolith angle needed for the diagnosis itself.

**Root cause (confirmed by direct code read, no subagent):** `digest/processors/event.rs:120-124` derives a new event's `digest_order` straight from `issue.digested_event_count` (a running counter, atomically `+1`'d per event via `UPDATE ... RETURNING` under the per-project advisory lock — safe under concurrency on its own). But `services/storage.rs:195-199` (data-retention cleanup, `POST /api/storage/cleanup`) **decrements** that same `digested_event_count` by the count of purged old events, treating it as a pure stat. Since old events (low `digest_order`) get purged while recent surviving events (high `digest_order`) stay, the decremented counter falls below digest_order values still occupied by surviving rows — next new event for that issue collides. Log pattern (dense collision band 3911-3931 for one issue_id, all within ~1s) matches exactly: counter reset landing inside still-live data. Every failed event is permanently lost (temp file cleanup still runs on error, no retry path exists in `ErrorProcessor::process`).

**Verified against real Sentry (subagent, sentry-repo SHA a32a33a5):** confirms the diagnosis and the fix direction — Sentry structurally never has this bug class:
- `Group.short_id` (Sentry's actual equivalent of `issues.digest_order`) is generated via a **dedicated** `sentry_projectcounter` table (`models/counter.py:43-127`, [permalink](https://github.com/getsentry/sentry/blob/a32a33a5106ce9350ccb33b406695f53067c4a9f/src/sentry/models/counter.py#L43-L127)) — atomic `INSERT ... ON CONFLICT DO UPDATE SET value = value + delta RETURNING value`, strictly increment-only (`raise ValueError` on non-positive delta — *"There is only one way, and that's up."*). Completely separate storage from any stat field.
- `Group.times_seen` (Sentry's equivalent of `digested_event_count`) is **never decremented anywhere** in `src/sentry/` — grepped `deletions/`, `tasks/deletion/` clean. Only additive writes or a full reset-to-`0` when reprocessing recreates the Group row from scratch (`reprocessing2.py:608-633`, [permalink](https://github.com/getsentry/sentry/blob/a32a33a5106ce9350ccb33b406695f53067c4a9f/src/sentry/reprocessing2.py#L608-L633)) — and even then `short_id` is copied verbatim to the new row while the code comments admit `times_seen` "is unlikely to be correct ootb." Sentry deliberately gives the identity field and the stat field different integrity guarantees.
- Sentry has **no per-issue sequence number for individual events at all** (no `digest_order` equivalent below the Group level) — events are UUID `event_id` + `group_id` FK, ordered by `(timestamp, event_id)` via Snuba/ClickHouse. Retention deletes whole Groups (`deletions/defaults/group.py:193-269`), never "purge old events, keep the group with an adjusted counter" — the exact pattern that broke Rustrak doesn't exist as a code path in Sentry.

**Recommendation given (not implemented — source investigation + advisory only, per Boundaries):** stop deriving event `digest_order` from `digested_event_count`; compute it from `SELECT MAX(digest_order) FROM events WHERE issue_id = $1` inside the same advisory-lock-protected transaction that already serializes issue creation (safe by construction, self-healing, no separate counter to desync). Leave `digested_event_count` as a pure decorative stat that retention can keep freely decrementing — same separation of concerns Sentry enforces between `short_id` and `times_seen`.

**Rustrak gaps confirmed:** new, high-severity — active data-loss bug in production (not yet in BOND.md's gap table since it's a Rustrak-internal bug, not a Sentry-compat divergence; noted in BOND.md's Rustrak Implementation State instead). No fix applied.
