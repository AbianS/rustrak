### DynamicSamplingContext (DSC) — deep-dived 2026-07-14, verdict: skippable
Relay parses `trace` field from envelope headers (`EnvelopeHeaders.trace: Option<ErrorBoundary<DynamicSamplingContext>>`, relay-server/src/envelope/mod.rs:112-114) into `DynamicSamplingContext` (relay-sampling/src/dsc.rs:25-74 — **relay-sampling added to sparse checkout this session, was missing before**). Full field table + envelope parsing + head-of-trace minting + sentry-trace/baggage clarification delivered to Abian this session (see sessions/2026-07-14.md for permalinks).

**Corrects a prior priority claim** (this file previously listed DSC as the 3rd blocking prerequisite before GH #180 AI Agent Monitoring, after span ingestion — that was wrong, not source-verified at the time). Source-verified now: DSC exists to let a fleet of untrusted multi-tenant Relays apply project-scoped probabilistic *dropping* rules while keeping one trace's sampling decision consistent, plus downstream bookkeeping (`client_sample_rate`/`server_sample_rate` measurements, `sentry.dsc.*` span tags) so undercounted metrics can be re-inflated after dropping. Rustrak drops nothing (self-hosted, single-tenant, keeps every event) — every DSC-dependent behavior in Relay is either N/A (no rule engine, no dropping) or trivially satisfied (100% keep rate is consistent by definition). Confirmed: `sentry-trace`/`baggage` HTTP headers are parsed by SDKs only, never by Relay's ingest endpoint — zero matches anywhere in relay-server/src. The `trace_id` needed for trace-waterfall reconstruction (Agents page, #180) already comes from each event/span's own payload fields (`contexts.trace.trace_id`, span `trace_id`) — Rustrak already extracts and stores this (PR #184, pre-existing transaction code) with zero DSC involvement. DSC's `trace_id` is only used to *validate* consistency against the payload's own trace_id (SpanV2 pipeline only, `Error::DynamicSamplingContextMismatch`), never to *supply* it.

Hard-required only in the opt-in SpanV2 pipeline, and even Relay's own comment calls that a protocol-conformance check, not a functional need: *"A DSC must be present. This is not a technical requirement as a missing DSC simply leads to a 100% sample rate."* (relay-server/src/processing/spans/dynamic_sampling.rs:54-58). Everywhere else (transactions, legacy_spans, metrics extraction) DSC is fully optional with graceful fallback.

**Recommendation for Rustrak**: do not implement DSC parsing as a #180 prerequisite — it isn't one. The only DSC-shaped work worth ever doing is cosmetic: reading `dsc.sample_rate` off transaction/span headers (a few lines) to show "this trace was client-side sampled at X%" in the UI, since Sentry SDKs may sample before sending even to a self-hosted server. Not blocking, not scheduled.
