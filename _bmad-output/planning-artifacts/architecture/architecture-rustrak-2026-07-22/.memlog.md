- (constraint) RESEARCH, arc42 Quality Model on Hexagonal Architecture (quality.arc42.org/approaches/hexagonal-architecture, page carries no date - currency unverified): names the exact failure mode feared here. 'An anemic core reduces use cases to pass-throughs: every call pays the indirection while no logic is protected.' Says to skip it 'for thin CRUD services and short-lived tools - the indirection and mapping tax exceeds the logic it protects', and quantifies the cost as 'three artifacts changing in lockstep for every added field'. - (constraint) RESEARCH, hard framework constraints that must shape the read/write split (Next.js server-actions guide 2026-06-23 and backend-for-frontend guide 2026-07-22): Server Actions are dispatched ONE AT A TIME PER CLIENT and are queued, so using them for data fetching forces sequential execution; 'do not rely on Promise.all to parallelize Server Actions from the client'. 'Fetch data in Server Components directly from its source, not via Route Handlers' - prerendered components calling a Route Handler FAIL THE BUILD. 'Treat every action as an untrusted entry point'; 'render-time gating is not a security boundary'; 'constrain return values... shape them to what the UI renders, not raw database records'. Conclusion: reads go through a plain server module called from Server Components, writes go through thin 'use server' actions that re-authorize.
- (constraint) RESEARCH, Next.js is deliberately unopinionated about structure (nextjs.org/docs/app/getting-started/project-structure, lastUpdated 2026-07-22): names exactly three equal-footing strategies - store project files outside app/ (app is routing only), store them in top-level folders inside app/, or split by feature or route - and says 'choose a strategy that works for you and be consistent'. - (constraint) RESEARCH, caching became a first-class cross-layer contract in Next 16 (nextjs.org/blog/next-16, 2025-10-21, plus server-actions guide 2026-06-23): 'use cache' / cacheTag / cacheLife are entirely opt-in behind cacheComponents. revalidateTag's single-argument form is deprecated and now wants a cacheLife profile. New updateTag() gives read-your-writes inside a Server Action; new refresh() refreshes uncached view state. A single action response can carry both data and a re-rendered RSC payload when it calls updateTag/revalidatePath/refresh, but revalidateTag with an SWR profile deliberately does NOT re-render. Cache tags span the read and write paths, so the tag vocabulary needs a named home in the architecture or it will drift. Rustrak uses none of this today and has cacheComponents off.
- (constraint) RESEARCH, blocker on any future caching: 'use cache' scopes CANNOT call cookies(), headers() or searchParams; they must be read outside and passed as arguments, or you get a prerender timeout / next-request-in-use-cache error. lib/rustrak.ts createClient() awaits cookies() internally, so today NO data path in the app can ever carry 'use cache'. - (constraint) GitHub issue rustrak/rustrak#204, OPEN, no comments, title 'Server Action errors are redacted in production, hiding all API error messages from users'. Root cause is React's design and is not configurable: only the digest crosses the server/client boundary, and the Flight client builds a NEW Error with a hardcoded message (resolveErrorProd, verified in next@16.2.10). The original message never leaves the server. Not reproducible in dev, since next dev keeps the real message, which is why it went unnoticed. Surfaced in #203 where an SMTP validation error was invisible and the reporter concluded their credentials were wrong. The rule that follows: throw means unexpected failure, redacted, handled by error.tsx; return means an outcome the user must read, and must be serialisable data.
- (constraint) Issue #204 measured scope: 81 Server Actions, of which 35 are called from Client Components. 25 of those 35 THROW and are broken in production. 10 already return a result object, in SIX DIFFERENT SHAPES. 28 toast.error sites render err.message.
